# HSN-derived taxonomy + locally-trained item classifier + GST rate lookup

## Context

Item categorisation and HSN matching in this app are both unreliable, and this session established
*why* — with measurements, not guesses:

- **Zero-shot embedding retrieval over CBIC tariff text does not work.** All 1,348 four-digit HSN
  headings are already embedded with `bge-m3` in pgvector. Probing the two known-answer items:
  - `WASHER TYPE : DISC SPRING ... SPRING STEEL 51CRV4` (correct: **7320**) returned
    7223 stainless wire, 8422 *dishwashing machines*, 8464 stone machine-tools, 8516 water heaters,
    7318 fasteners. Correct class **not in top-5**. Best similarity only 0.5736.
  - `SOCKET MATERIAL : MILD STEEL ... IS:1239` (correct: **7307**) — also **not in top-5**.
- **Enriching each heading with its 6/8-digit descendants helps, but nowhere near enough.** In a
  5-way comparison the correct class ranked first by a margin of **0.001** (7320 = 0.5250 vs
  7318 = 0.5239). That is a coin flip, not a classifier.
- **The root cause is vocabulary, not tuning.** Heading 7320's descendants say "LEAF-SPRINGS",
  "HELICAL SPRINGS", "COIL SPRING", "SPRING PINS" — the tariff text **never** contains "disc spring"
  or "Belleville washer". This is a knowledge-mapping problem, so no amount of similarity search
  over the official text will solve it.

That explains the whole chain of symptoms: ANN retrieval offers garbage candidates, the LLM picks
the least-bad garbage, and the hand-written keyword rules added earlier (7307, 7320) were patching
individual holes in a retrieval step that was broken generally.

Separately, **GST rates in this app are fabricated**. There is no HSN→rate table anywhere; the rate
is an LLM guess snapped to `GST_SLABS = [0, 5, 12, 18, 28]` in `boq-enrichment.service.ts`, plus two
hardcoded `?? 18` fallbacks. Those slabs are **stale** — Notification 9/2025-CT(Rate), effective
22 Sep 2025, restructured GST into seven schedules (5 / 18 / 40 / 3 / 0.25 / 1.5 / 28) and merged
the 12% slab away.

**Outcome intended:** one trained model that, from a messy procurement line, returns a chapter, a
4-digit heading (which *is* the HSN code), and — via a curated lookup sheet — the GST rate. All
training data, test data and accuracy reports live in the repo so they can be reviewed and shared
with clients, and a Settings button re-runs the whole pipeline after the user edits the sheet.

**Decisions taken by the user in planning:** full HSN taxonomy (all 1,379 headings, not pruned);
hand-authored lexicon for the chapters actually bought plus LLM-generated coverage for the tail;
train in Python on Metal and export to ONNX for in-process Node inference (no new service);
artifacts under `ml/` in the repo.

## 1. The lookup sheet — single source of truth

`ml/data/hsn-gst-lookup.xlsx`, generated once from the CBIC data already in Postgres, then owned and
edited by the user. Everything downstream (taxonomy, rates, training vocabulary) is rebuilt from it.

| Column | Purpose |
|---|---|
| `code` | 2-digit chapter or 4-digit heading |
| `level` | `chapter` \| `heading` |
| `parent_code` | chapter for a heading, blank for a chapter |
| `official_description` | verbatim CBIC text (regenerated on refresh; not hand-edited) |
| `display_name` | **editable** short label for dropdowns — generated by truncating at the first `;`/`:`/`,` clause and capped, because the raw text runs to 1,210 chars |
| `gst_rate` | **editable** percent |
| `rate_source` | `notification-9/2025` \| `chapter-default` \| `manual` — so the user can see what is authoritative vs. defaulted |
| `effective_from` | date the rate applies from |
| `active` | lets the user hide chapters they never buy without deleting coverage |
| `trade_terms` | **editable, semicolon-separated real-world names** — e.g. `7320: disc spring; Belleville washer; cup spring; preload spring`. This is the lexicon, exposed to the user. |

`trade_terms` is the point of the edit-and-retrain loop: correcting a misclassification is a matter
of adding the trade name to the right row and clicking Update, rather than asking an engineer for a
new keyword rule. The existing hand-written rules in `hsn-keyword-rules.ts` (7307, 7320) migrate into
this sheet as seed rows and that file is retired.

**GST seeding is curation, not a feed.** Notification 9/2025-CT(Rate) lists entries at mixed
granularity (tariff item, sub-heading, heading *or* chapter), and CBIC publishes no machine-readable
HSN→rate file — `cbic-gst.gov.in` now just redirects to `taxinformation.cbic.gov.in`. So the
generator seeds a chapter-level default per the notification's schedules, adds heading-level
overrides for the hot chapters, stamps every row with `rate_source`, and the user corrects from
there. The sheet is authoritative; the seed is a starting point, and the plan should say so in the
sheet's own header row.

## 2. Database changes

`packages/database/prisma/schema.prisma` — **hand-write the migration**, and use `prisma migrate
deploy` or `migrate dev --create-only` (per CLAUDE.md, plain `migrate dev` offers a corrective
migration that would drop the HNSW indexes).

- `Category`: add `code String?`, `officialDescription String?`, `gstRate Float?`,
  `active Boolean @default(true)`. Add `@@unique([code])`; **drop `@@unique([parentId, name])`** —
  15 heading descriptions repeat inside a chapter, so name uniqueness cannot hold.
- `HsnCode`: add `gstRate Float?` and `gstRateSource String?`, populated from the sheet.
- New `ClassificationRun` table mirroring the existing `ReferenceDataImport` pattern:
  `id`, `stage`, `status`, `message`, `trainedRows`, `evalAccuracy`, `evalTopK`, `baselineAccuracy`,
  `deployed Boolean`, `runPath`, `triggeredById`, `startedAt`, `finishedAt`. This is how the UI shows
  progress — the codebase has **no** job-progress mechanism today (`job.updateProgress` is used
  nowhere), and `ReferenceDataImport` + a status endpoint is the established precedent.

**Taxonomy swap.** The current tree is 7 parents / 38 leaves from `STARTER_TAXONOMY` in
`packages/database/prisma/seed.ts:37`. Replace it with 98 chapters / 1,379 headings built by bulk
insert from the sheet (the seed's find-or-create loop would issue ~1,477 sequential queries — build
this as an importer, not seed logic). Only 8 items are category-confirmed, so re-classify rather than
attempt a mapping; keep legacy rows only where an `Item.categoryId` still points at one, and mark
them `active = false`.

`flattenLeaves` in `categories.mapper.ts` needs **no change** — it defines a leaf as a childless row,
and headings are childless. `buildPathMap` produces `"Chapter > Heading"`, which keeps
`boq-enrichment.service.ts`'s `path.split(" > ")` working, provided `display_name` is what lands in
`Category.name`.

## 3. `ml/` layout

```
ml/
  data/
    hsn-gst-lookup.xlsx          # the sheet (git-tracked)

    generated/{train,val,test}.jsonl   # built datasets (git-tracked — text, reviewable, diffable)

  train/                         # python, uv-managed (pyproject.toml + lockfile, git-tracked)
  runs/<timestamp>/              # metrics.json, confusion.csv, report.md, model/  (gitignored)
  models/current/                # deployed onnx + tokenizer + labels.json      (gitignored)
```

`.git` is currently **16 MB**. Datasets and reports are text and belong in git; model binaries
(~90 MB+ per run) do not — gitignore `ml/runs/*/model/` and `ml/models/`. The deployed model is
rebuilt by the pipeline, so it is reproducible rather than versioned.

## 4. The model

**A trained bi-encoder over class prototypes — not a 1,379-way softmax head.**

That choice is driven by this specific situation, and it is the most important decision in the plan:

- Training examples per heading average 16 but bottom out at **1**. A softmax head cannot learn a
  class from one example; a bi-encoder still places it correctly, because the class is represented by
  its *own text* (prototype), not only by examples of it.
- The user edits the sheet and clicks Update. With a softmax head, adding or splitting a heading
  changes the output dimension and forces a full retrain. With prototypes, a changed heading just
  needs its prototype re-embedded — the edit-and-rerun loop stays cheap and the model stays valid.
- It reuses infrastructure that already exists. Prototypes are vectors in pgvector, retrieval is the
  same ANN query the app already runs. The Node side gains an embedder, not a classifier.

**Checkpoint:** `intfloat/multilingual-e5-small` — 118M params, 384-dim, 12 layers. Small enough to
fine-tune comfortably on a 16 GB M1 Pro that is also hosting Docker and Ollama, strong on short noisy
text, and multilingual (real item text carries transliterated and Hindi fragments). Fallback if MPS
memory is tight: `BAAI/bge-small-en-v1.5` (33M, 384-dim).

**Training objective:** InfoNCE / MultipleNegativesRankingLoss — pull an item text toward its own
heading's prototype, push it away from in-batch negatives plus explicit hard negatives. Hard-negative
pairs are seeded from the known traps: **7307 vs 7304/7306** (fittings vs. raw tube) and
**7318 vs 7320** (fastener washers vs. disc springs — CBIC 7318's own text literally reads "washers
(including spring washers)", which is exactly what misleads a similarity model, and is the
documented cause of the wrong codes on tender 1400014205).

**Prototype text per heading** = official heading description + all 6/8-digit descendant descriptions
+ the sheet's `trade_terms`. That last part is what closes the vocabulary gap this document opened
with: "disc spring" and "Belleville washer" exist nowhere in CBIC's text, so they must be supplied.

**Hyperparameters** (starting point, to be tuned against the eval set): max_seq_len 128 (items are
short), batch 64 (in-batch negatives want a large batch), LR 2e-5, AdamW, 10% warmup, 4 epochs,
early stopping on real-eval recall@1. Expect tens of minutes per run on MPS at this size — it should
be measured on the first run and recorded, not asserted.

### Dataset construction

`ml/data/generated/{train,val,test}.jsonl`, one object per line:
`{ "text": "...", "heading": "7320", "chapter": "73", "source": "tariff|lexicon|llm|real", "weight": 1.0 }`

Four sources, in descending trust order:
1. **`tariff`** — the official text: each heading's own description and each descendant's description,
   with the parent's text prepended where the child is uninformative (many 6-digit rows are literally
   "OTHER" or "FLANGES" and are meaningless alone).
2. **`lexicon`** — hand-authored trade vocabulary in `ml/data/lexicon/<chapter>.yaml` for the hot
   chapters (**39, 40, 68, 70, 72, 73, 74, 76, 82, 83, 84, 85, 90**), written in the phrasing real
   tenders actually use — including the spec-soup format observed in this app
   (`WASHER TYPE : DISC SPRING MATERIAL : : SPRING STEEL ...`), not clean product names.
3. **`llm`** — bulk paraphrases for the remaining ~85 chapters, generated with the local Ollama models
   already installed. Lower weight, and never used in the eval set.
4. **`real`** — actual app items with human-confirmed codes. Eval only; never trained on.

Class imbalance (1 to 255 descendants per heading) is handled by capping examples per class and
weighting, not by discarding classes.

### The eval set is real, and it is the gate

`ml/data/eval/real-items.csv` — real BOQ lines with hand-checked labels. 120 BOQ items and 20
HSN-confirmed catalog items exist today; the two probe items in the Context section go in as named
regression cases. Synthetic-vs-synthetic accuracy is meaningless here and will not be reported as
headline accuracy. The set grows over time from the app's existing `ITEM_CLASSIFIED` audit-log
entries, which already record what was predicted and what a human confirmed.

**Two baselines must be built first and beaten**, or the fine-tune does not ship:
1. Frozen `bge-m3` + prototype cosine — this is the current system, already measured failing (correct
   class not in top-5 on both probes).
2. Frozen `bge-m3` + a linear probe on the same training set — the cheap supervised floor.

### Calibration and abstention

The app's standing rule is that an uncertain AI value never auto-writes into a real field, so the
model must say when it does not know. Fit a small logistic calibrator on two features — top-1 cosine
and the top-1-minus-top-2 margin — against correctness on the eval set, giving a real probability.
Choose the abstention threshold for a **target precision** (e.g. ≥95% precision on what it does
answer), and report the resulting coverage. Below threshold the item is left unclassified rather than
guessed. The 0.001-margin case in the Context section is precisely what this must catch.

## 5. Node-side inference

New `apps/server/src/modules/classification/` module, loading the model once at boot and exposing
`classify(text) → { chapterCode, headingCode, confidence, abstained }`.

**Library:** `@huggingface/transformers` (Transformers.js, now v4 on npm) with its `feature-extraction`
pipeline pointed at a **local directory**, not the Hub. It bundles the tokenizer and runs
`onnxruntime-node` underneath, which avoids hand-porting the tokenizer — the part most likely to
silently disagree with training and produce quietly wrong vectors. Export via Optimum / the official
`scripts.convert --quantize` path; int8 quantisation puts an e5-small ONNX in the tens of MB with a
negligible accuracy cost at this model size.

**Prototype storage:** a new `prototypeVector` column sized to the model (384-dim) on `HsnCode`,
with its own HNSW cosine index — *not* the existing 1024-dim `embeddingVector`, which belongs to
`bge-m3` and is still used elsewhere. Hand-write that index migration; per CLAUDE.md, Prisma cannot
express an index on an `Unsupported(...)` column and plain `migrate dev` will offer a corrective
migration that drops the existing HNSW indexes.

Wire-in points, all of which already exist and should be *changed*, not duplicated:
- `boq-enrichment.service.ts#classifyCategory` — replace the closed-vocabulary LLM call. Its current
  prompt (`buildClassifyPrompt`) renders **every leaf id + path into the prompt**; that is fine at 38
  leaves and impossible at 1,379, so this call has to go regardless.
- `boq-enrichment.service.ts#matchHsnCode` — the heading *is* the HSN code, so the ANN+LLM pick and
  the `hsn-keyword-rules.ts` overrides both retire.
- `items.service.ts#suggestForItem` Rung 2 — same substitution. **Rung 1 stays**: sibling reuse via
  `pickConfirmedMatch` (cosine + `sameSpec()` + unit) is a confirmed-human-decision path and should
  continue to outrank the model.
- GST: `suggestedGstRate` comes from the matched heading's `gstRate`, not an LLM guess. Fix
  `GST_SLABS` to the post-22-Sep-2025 set and remove the two hardcoded `?? 18`
  (`items.repository.ts:171`, `packages/types/src/boq.ts:9`).

## 6. The Settings "Update" button

`POST /reference-data/classification/rebuild` (`settings:manage`) enqueues on a new
`classificationRebuildQueue`. The existing HSN refresh runs **synchronously inside the request** —
that ceiling is already reached and a fine-tune cannot live in an HTTP request.

Worker stages, each writing progress to `ClassificationRun`:
1. Read `ml/data/hsn-gst-lookup.xlsx` **from disk** (the user edits it in place; this is not an
   upload dialog).
2. Rebuild `Category` tree + `HsnCode.gstRate` from the sheet.
3. Regenerate `ml/data/generated/*.jsonl` from sheet + lexicon + LLM tail.
4. Shell out to the Python trainer — same pattern as `pdftotext` in `shared/utils/pdf-text.ts`, the
   established precedent for "native thing Node can't do".
5. Evaluate against the real eval set **and the previous run**. Refuse to deploy a worse model.
6. Swap `ml/models/current/`, hot-reload the model in the server.
7. Re-classify catalog items and current BOQs.

Settings page gains a "Classification model" card next to the HSN/SAC card: last run, accuracy,
whether it deployed, and an Update button — following `HsnSacCard` in
`apps/web/src/app/(dashboard)/settings/page.tsx` exactly.

**Note:** only 2 of the 18 settings are actually live-wired (`AI_MATCH_THRESHOLD`,
`HSN_SAC_AUTO_REFRESH_ENABLED`); the other 16 are written to the DB but every consumer still reads
`env.*`. Any new setting here (model path, abstention threshold) must be read through
`settingsService.get` or it is decoration.

## 7. Build order

This is large, so it ships in stages that each stand on their own. Every stage ends green
(typecheck/lint/test) and is independently useful, so it can stop early without leaving rubble.

1. **Sheet + taxonomy + rates, no model.** Generate `hsn-gst-lookup.xlsx`, migrate `Category` and
   `HsnCode`, build the importer, swap the taxonomy, wire `gstRate` into BOQ enrichment, fix the
   stale `GST_SLABS` and the two hardcoded `?? 18`. *Value on its own: GST rates stop being invented,
   and the taxonomy becomes HSN-aligned.* Classification still uses today's path at this point.
2. **Datasets + baselines.** Build `ml/`, author the lexicon for the hot chapters, generate the
   datasets, assemble the real eval set, and measure both baselines. *Value on its own: the first
   honest accuracy number this feature has ever had.*
3. **Train, export, evaluate.** Fine-tune on MPS, export ONNX, calibrate, produce
   `ml/runs/<ts>/report.md`. Ship only if it beats the baselines on the real eval set.
4. **Node inference + wire-in.** `classification` module, prototypes into pgvector, replace
   `classifyCategory` / `matchHsnCode` / `suggestForItem` Rung 2. Retire `hsn-keyword-rules.ts`.
5. **The Update button.** `ClassificationRun`, queue, worker stages, Settings card.

Stage 1 is worth doing regardless of whether the model ever beats its baseline.

## 8. Risks, honestly

- **The fine-tune may not beat the baseline.** Most of the training signal is synthetic, and
  synthetic text can teach the model to match *its own generator's* phrasing rather than real tender
  text. This is why stage 3 is gated on the real eval set and why stage 2 ships the baselines first.
  *Fallback:* keep the enriched-prototype retrieval (measurably better than today) plus the
  `trade_terms` lexicon as a deterministic pre-match — that alone fixes the cases seen so far, and it
  is the existing keyword-rule idea generalised and put under the user's control.
- **The eval set is small** (≈140 real items). Accuracy from it has wide error bars; report it as
  counts, not just percentages, and grow it from the audit log before drawing conclusions.
- **1,379 classes in a dropdown is a lot of UI.** The `active` flag and chapter grouping mitigate it,
  but the category picker in `items/categories/page.tsx` and the BOQ grid will need a searchable
  selector rather than a plain list.
- **Memory.** Training happens on the same 16 GB machine that is running Docker (Postgres, Redis,
  MinIO) and Ollama with models resident. The trainer should be run with those idle, and the plan
  should verify actual peak memory on the first run rather than assume.
- **A stale worker silently runs old code.** Already bitten once this session: the BullMQ worker had
  been running pre-fix code for days, and separately the main checkout's Prisma client was stale
  after a new model was added. Any stage that changes the schema or the worker must restart
  `pnpm dev` and re-run `pnpm db:generate`, and the verification step must confirm it took.
